# Maintenance-aware content marker resolution

2026-10-05; SPIKE-001 small native prototype, unchanged existing warehouse. [Databricks documentation](https://learn.microsoft.com/en-us/azure/databricks/tables/operations/custom-metadata) says session commit-metadata settings are unsupported on serverless compute; no unsupported configuration was applied. This prototype instead uses a durable row marker committed atomically with current/journal/receipt rows.

Three private catalog-managed tables start from seeded snapshots. Deterministic ALTER TABLE metadata-only commits advance current once and journal twice before the data transaction, then advance each again afterward. These are controlled table metadata changes, not an assertion about OPTIMIZE initiator or automatic maintenance. The publisher closes its session; an independent resolver reads the batch receipt and enumerates complete retained history after the baseline, checking marker presence at each actual version. It resolves the earliest marker-containing snapshot, verifies subsequent marker persistence, and checks full current/journal payload and old snapshot contents.

Resolved current **3**, journal **4** match independently observed transaction commits. They differ from naive prior+one **2/2** and latest **4/5**. All native controls pass; marker receipt persists through session restart. This demonstrates the selected monotonic-content case, not a general current-state version allocator. No later logical writes occur; a production unresolved-publication barrier must enforce that prerequisite. Missing history, marker removal by later changes, duplicate marker writers, reused batch IDs, deletions without canonical carriers and competing publishers must cause refusal or use other authoritative commit evidence. History retention and resolver read costs remain material.
