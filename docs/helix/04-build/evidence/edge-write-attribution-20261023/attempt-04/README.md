# Attempt 04: bounded JFR sample of the `.4` edge write

One local 225M-edge INSERT completed under the reviewed polled supervisor: 54.4 seconds total, 2,599,188,649 output-tree bytes and 10,055,932 diagnostic bytes. No limit fired. The limits are polling thresholds, not filesystem quotas. Runtime was Python 3.12.14, Spark 4.2.0, Delta 4.4.1, JDK 21.0.13.0.2, `local[18]`, 24g driver heap. This is one diagnostic sample, not a throughput claim or full-scale qualification.

The Delta footer reports 225,000,000 rows across 18 ZSTD parquet files totaling 2,569,031,961 active bytes; an independent file recount agrees. The physical write was nested SQL execution 9 (`rootExecutionId` 8), job 4, stage 6 under outer append execution 8. Stage 6 observed all 18 tasks and the full output record/byte totals. It spanned 33.565 seconds within the outer execution's 35.569 seconds. Executor metrics report 341.483 CPU-seconds and 11.755 task-seconds of JVM GC; no spills.

The JFR recording spans the full outer INSERT: recording became ready 129.633 ms before SQL start; stop began less than 1 ms after SQL completion. It contains 6,729 execution samples, 1,387 native-method samples and 9,877 object-allocation samples. The leading execution-sample method is Parquet `Binary.lexicographicCompare` (629 samples, 9.35%). Allocation pressure is led by `byte[]` (45.89%) and `UTF8String.getBytes()` (19.62% at the allocation-site view). These are JVM-wide samples, not task-scoped measurements; allocation pressure is weighted sampled volume, not allocation count. The leading `Binary.lexicographicCompare` samples pass through `BinaryStatistics.updateStats`, without attribution to a specific column or dictionary encoding. Byte conversion and Parquet comparison are follow-up leads only; this profile does not establish causality or separate compression from IO.

Exact run bounds, SQL and nested lineage, footer, timing, JFR event counts and limitations are in [experiment.json](experiment.json). Raw JFR, event stream, plan, exact executed SQL, progress, profile settings and supervisor receipt are retained beside it. `hot-methods.txt`, `allocation-by-class.txt` and `allocation-by-site.txt` are `jfr view` summaries from the retained recording. [SHA256SUMS.txt](SHA256SUMS.txt) binds packet files. After verification, only this attempt's owned `out/warehouse` data was removed; JFR, event stream and receipts remain in the private attempt root. No Spark rerun was performed.
