# R05 end-to-end budget and materialization design (2026-10-23)

**Status:** Offline evidence synthesis and proposal. No Spark, graph engine, cloud workload, or data write was run for this packet. It does not authorize the held 1B/5B trial.

## Decision context

R05 requires a full canonical `.4` synthetic Delta fixture, two exact point lookups, two scans of the persisted representation for row and endpoint-formula witnesses, and one actual bounded graph-engine action. The 15-minute value is an owner-review trigger, not a hard maximum. Before any full run, present the 80%-of-measured-rate estimate together with other operation times, resource bounds and costs; if the projected write exceeds 15 minutes, obtain an explicit owner decision. The desired end-to-end time is “a few minutes,” not a formally measured SLO. The PRD's assumed 5B-edge count remains a planning assumption. See the [PRD](../../../01-frame/prd.md), [CONTRACT-001](../../../02-design/contracts/CONTRACT-001-publication-boundary.md), [CONTRACT-002](../../../02-design/contracts/CONTRACT-002-consumer-read-boundary.md), [CONTRACT-003](../../../02-design/contracts/CONTRACT-003-delta-graph-tables.md), [CONTRACT-004](../../../02-design/contracts/CONTRACT-004-publication-resolver.md), [TD-006](../../../02-design/technical-designs/TD-006-managed-current-incremental-publication.md), [TD-007](../../../02-design/technical-designs/TD-007-native-xxhash64-lookup-layout.md), and [TD-008](../../../02-design/technical-designs/TD-008-pinned-delta-graphframes-scale-action.md).

The full Delta `.4-xxhash64` profile remains selected. Its `lookup_hash BIGINT` is a pruning accelerator; source-qualified type/ID tuples and independent edge IDs remain authoritative. Exact values, edge multiplicity, endpoint validity, table versions and protocol must be retained. Do not reduce the carrier, replace identities with hashes, disable predictive optimization, handcraft Delta log actions, or relabel the synthetic fixture as source/publication evidence.

## Known time and byte budget

The current selected-profile reference is the [18-core calibration](../current-upstream-release-20261021/local-current/canonical-carrier-xxhash64-18core-calibration-20261021.json), cross-checked in the [R05 storage reassessment](../r05-storage-throughput-reassessment-20261023/README.md). It measured 45M nodes and 225M edges on Spark 4.2.0, Delta 4.4.1, Python 3.12.14, JDK 21.0.13, `local[18]`, 18 partitions and ZSTD. Parquet footers confirmed 45M and 225M rows, with 18 files per role; combined active bytes were 3,062,253,112. This was synthetic data, including `source_position=id` and decimal-string delivery IDs.

At the historical selected-profile curve, writes alone are 3.61 times a five-minute illustrative budget. Even the unpromoted Parquet-statistics sensitivity is 3.29 times that budget before reads, scans, GraphFrames, validation, or cleanup. If node time remained 268.877 s, the five-minute scenario would leave 31.123 s for five billion edges, requiring about 26.15 times the selected-profile edge throughput. These ratios are arithmetic sensitivities, not performance promises. Falling below the 15-minute write review trigger would still not demonstrate a few-minute end-to-end run.

The target active-Parquet estimate is 68.050 GB by row-linear arithmetic. It excludes transaction logs, staging, concurrent retained versions, working space, event logs and extra outputs. At the calibration's 18 files per role, 64 MiB target-file-size remains a hint, not the observed file maximum; the separate attempt-03 edge attribution found 18 ZSTD files, 36 row groups and 2,569,031,961 bytes for 225M rows, or about 142.7 MB per file and 6.25M rows per row group. Extrapolated file counts are not a commitment: data distribution and runtime may change geometry.

## What the write instrumentation says

The exact synthetic writer is retained as [`attempt-03/insert.sql`](../edge-write-attribution-20261023/attempt-03/insert.sql): Spark `range(225000000)` feeds a single projected `.4` edge row shape, computes native typed `xxhash64`, then inserts into the Delta table. Its projected fields include endpoint arithmetic, JSON payload placeholders, a synthetic `source_position=id`, and `CAST(id AS STRING)` delivery IDs. This direct synthetic path does **not** exercise the production publisher's JSON `explode(from_json(:rows,...))` staging in [`graph_sql_plan`](../../../../../src/ashlar_host/graph_sql.py). The measured fixture therefore cannot estimate source parsing, accepted-page serialization, or publisher costs.

Attempt-03's INSERT took 26.354 s. Its nested write job/stage produced 225M rows and 2,569,031,961 bytes in 18 tasks over a 25.485 s stage span, with 310.684 executor CPU-seconds, 424.703 summed task-seconds and 11.277 task-seconds of task GC. The stage occupied 96.7% of INSERT wall time; the 0.869 s remainder is residual, not isolated commit time. Tasks lasted 21.763–25.466 s; there was one 18-task output stage, no memory or disk spill, and limited observed task-duration spread. These measures do not prove the machine was CPU-saturated or identify storage as the bottleneck.

Attempt-04 repeated the unchanged edge write with a JVM-wide JFR window spanning INSERT. It is a profiled diagnostic, not a comparable throughput run. Its samples lead with Parquet binary comparison/statistics and UTF8-to-byte conversion, but stacks do not identify a specific input column or establish compression-versus-I/O causality. The per-column statistics pair then showed the exact effect for `source_delivery_id`: 36/36 Parquet chunks had regular stats in baseline and 0/36 in candidate, while selected Delta statistics and the exact one-row full-key result matched. The measured 6.31 s insert difference is not a repeatable gain; bytes fell by only 238,615 (0.0093%), and candidate stage CPU fell about 3.3%. No further writer setting is supported by current evidence.

The already-adopted `.4` `BIGINT` lookup hash is the substantial encoding change supported by TD-007; prior small-fixture results found the old SHA-256 string dominated Parquet size. It is included in the current calibration and cannot be counted again as a future improvement. The hash-range and identity-sort layout samples were both larger/slower than the sequential-identity baseline and are not selected. The data does not support replacing the carrier, promoting the single stats pair, lowering ZSTD effort, or assuming more cores will scale linearly.

## Supported materialization proposal

The largest governed way to avoid redundant materialization is to pass the two pinned Delta DataFrames directly into a transient GraphFrames view, then execute the bounded seed action. This is the TD-008 design and the direction of `src/ashlar_host/pinned_delta_graphframes.py`; it avoids routing six billion logical records through the 10,000-row JSON release or separately materializing a graph copy. Use source-qualified struct vertex keys `(source_system,type_id,id)` and retain independent edge identity `(source_system,rel_type_id,id)`. Preserve parallel edges and the canonical carrier values; do not collect either input frame, convert to GraphX, or persist another graph copy.

This is a no-duplicate-export design, not a fix for the current Delta write rate. The bytes and time avoided by not separately materializing a graph copy are unmeasured; the design does not change Delta materialization rate. Its actual GraphFrames scan, shuffle and action cost remains unknown, and any end-to-end saving requires a comparable measurement. The current canonical `.4` holder packet is offline and does not yet provide execution proof for the canonical fixture; the existing 3-node/2-edge smoke establishes only a tiny compatibility slice.

Before attempting a canonical action, first check the mapping and independent oracle inertly. Then use a tiny correctness discriminator whose independently frozen expected bag covers overlapping local IDs from two sources, an isolated node, a self-loop, parallel edges with different edge IDs, and exact endpoint formulas. Check the transient vertex/edge schemas, preserve all selected payload values, verify changed-version and expired-custody refusals, cap output at `cap+1` and refuse overflow, and compare the complete small edge-occurrence bag. Reuse actual `.4` carrier rows and the selected pinned Spark/Delta/GraphFrames/JDK artifacts. This is a small implementation discriminator only; it does not qualify the generator at scale, retained files, production data, publication, ACK, or managed Unity Catalog.

## Measurement plan and acceptance gates

When the held trial is eventually admitted, use one deterministic generator and exactly one full materialization per role. Keep a single run ledger with monotonic timestamps and disjoint intervals for startup, table DDL, node write, edge write, two point reads, row/count scan, endpoint-formula scan, GraphFrames frame construction/action, footer/Delta validation and cleanup. Record the exact physical plans, runtime/JAR identities, generated source digest, selected versions, rows, actual bytes, file/row-group geometry, task/stage CPU and wall times, spill/GC, input-file metrics, shuffle, bounded result bag, output caps and cleanup outcome. Attribute overlapping GraphFrames scans by stage/SQL execution identity; do not add nested clocks twice. Include all workspace/log/Delta-log/output bytes in resource accounting.

Keep these scopes separate:

- **R05 owner review:** before a full run, present the selected-profile 80%-rate write estimate and a conservative full-pipeline budget with other operation times, resources, output and cleanup bounds. The current selected-profile write-only estimate is 18.05 minutes, and the nonselected stats sensitivity is 16.425 minutes; either projection above 15 minutes requires an explicit owner decision after review. The 15-minute value is a review trigger, not a hard cap.
- **Few-minute end-to-end target:** after a proposed numeric limit is owner-selected, compare measured total wall time—not write-only extrapolation—to it, including validation and cleanup. Current evidence has no full scan or canonical GraphFrames timings, so it cannot qualify this target.
- **Semantic pass:** require exact persisted row counts and independently derived endpoint validity, two exact point results, two actual scan witnesses, one bounded actual graph-engine result, and unchanged full `.4` values/edge multiplicity. Footer or Delta-log metadata alone is not a graph result or source-custody proof.

## Open evidence and stop conditions

No evidence currently supplies target-size read bytes, two scan durations, GraphFrames action plan/runtime cost, full validation time, cleanup time, or an end-to-end attempt. Source payload entropy also differs from the synthetic constant JSON and decimal delivery IDs. The production source/ACK path and managed Unity Catalog publication remain separate proofs under R05; this local synthetic trial cannot close them.

Before a 1B/5B run, present the current estimate, full-pipeline costs and resource ceiling to the owner; if the selected-profile write estimate exceeds 15 minutes, obtain an explicit owner decision after review. Do not start Spark while the shared native slot is occupied. First clear canonical fixture generator/oracle correspondence, actual runtime/JAR admission, retained-file/exclusive-use custody and the tiny correctness discriminator required by TD-008. Preserve any run outcome and revisit measured work if the resulting cost is not acceptable; do not weaken Delta or graph semantics to force a timing target.
